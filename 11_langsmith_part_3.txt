LANGSMITH @TRACEABLE INTERVIEW QUESTIONS & ANSWERS

============================================================
1. WHAT IS @TRACEABLE IN LANGSMITH?
============================================================

Answer:

@traceable is a LangSmith decorator that automatically captures
and tracks the execution of a function.

When a function is decorated with @traceable, LangSmith records:

- Function Input
- Function Output
- Execution Time
- Metadata
- Errors
- Function Name

and stores it as a separate Run inside a Trace.

Example:

@traceable
def retrieve_documents(query):
    pass

Whenever this function executes, LangSmith creates a separate run
for it in the trace.

------------------------------------------------------------
Interview One-Liner
------------------------------------------------------------

@traceable automatically traces a function and records it as an
individual run inside a LangSmith trace.

============================================================
2. WHY DO WE USE @TRACEABLE?
============================================================

Answer:

In production AI applications, a request usually passes through
multiple business functions.

Example:

User Query
    ↓
Document Retrieval
    ↓
Prompt Creation
    ↓
LLM Call
    ↓
Response Generation

Without @traceable, debugging becomes difficult because all steps
appear merged together.

With @traceable, every function can be monitored separately.

Benefits:

- Easier debugging
- Better observability
- Performance analysis
- Latency tracking
- Error tracking

============================================================
3. WHAT HAPPENS IF WE DON'T USE @TRACEABLE?
============================================================

Answer:

Without @traceable, LangSmith may only show model calls and limited
execution details.

Example:

Trace
 └── LLM Call

Developer cannot easily identify:

- Retrieval issues
- Prompt issues
- Business logic failures

Root cause analysis becomes difficult.

============================================================
4. WHAT HAPPENS WHEN WE USE @TRACEABLE?
============================================================

Answer:

Each decorated function becomes an independent run.

Example:

@traceable
def retrieve_documents():
    pass

@traceable
def create_prompt():
    pass

@traceable
def call_llm():
    pass

LangSmith View:

Trace
│
├── retrieve_documents
│
├── create_prompt
│
├── call_llm
│
└── Final Response

Each function is visible separately.

============================================================
5. DOES EVERY @TRACEABLE FUNCTION CREATE A NEW TRACE?
============================================================

Answer:

No.

A common interview confusion.

@traceable does NOT create a new trace.

It creates a Run inside the existing trace.

Relationship:

Trace
    ├── Run 1
    ├── Run 2
    ├── Run 3

Each @traceable function becomes one run.

------------------------------------------------------------
Interview One-Liner
------------------------------------------------------------

One Trace can contain multiple Runs generated by @traceable
functions.

============================================================
6. DIFFERENCE BETWEEN THREAD, TRACE, RUN, AND @TRACEABLE
============================================================

Answer:

Thread
-------
Complete conversation session.

Trace
------
Single user request execution.

Run
----
Individual step inside trace.

@traceable
----------
Automatically creates a run.

Hierarchy:

Thread
│
├── Trace 1
│     ├── Run
│     ├── Run
│     └── Run
│
├── Trace 2
│     ├── Run
│     └── Run
│
└── Trace 3

Memory Trick:

Thread > Trace > Run > @traceable

============================================================
8. HOW DOES @TRACEABLE HELP IN RAG DEBUGGING?
============================================================

Answer:

Most RAG failures occur before reaching the LLM.

Common failures:

- Wrong chunk retrieval
- Poor embeddings
- Incorrect metadata filtering
- Prompt generation issues

When each function is traced separately, developers can determine:

Was retrieval successful?

Was reranking successful?

Was prompt generated correctly?

Did LLM generate wrong output?

Thus troubleshooting becomes easier.

============================================================
9. WHAT INFORMATION DOES LANGSMITH CAPTURE FROM A
@TRACEABLE FUNCTION?
============================================================

Answer:

For every traced function LangSmith captures:

- Function Name
- Input Parameters
- Output Result
- Execution Duration
- Start Time
- End Time
- Error Details
- Metadata

This helps in deep debugging and observability.

============================================================
10. HOW DOES @TRACEABLE HELP IN PERFORMANCE OPTIMIZATION?
============================================================

Answer:

Suppose application takes 20 seconds.

Without @traceable:

No idea which component is slow.

With @traceable:

retrieve_documents() : 2 sec

rerank_documents() : 1 sec

generate_embeddings() : 8 sec

call_llm() : 9 sec

Developer can immediately identify bottlenecks.

============================================================
11. CAN @TRACEABLE HELP FIND ERRORS?
============================================================

Answer:

Yes.

If a function throws an exception, LangSmith captures:

- Function name
- Stack trace
- Input values
- Error details

This significantly reduces debugging effort.

============================================================
12. SHOULD EVERY FUNCTION BE DECORATED WITH @TRACEABLE?
============================================================

Answer:

No.

Only important business functions should be traced.

Examples:

✓ Retrieval Functions

✓ Tool Functions

✓ Prompt Builders

✓ Vector Search Functions

✓ Agent Functions

✓ LLM Wrappers

Not usually needed for:

✗ Small Utility Functions

✗ Simple Formatting Functions

✗ Mathematical Helpers

Overusing @traceable can make traces noisy.

13. INTERVIEW SCENARIO QUESTION
============================================================

Question:

A user receives a wrong answer in a RAG application.
How would @traceable help?

Answer:

I would decorate key stages such as retrieval, reranking,
prompt construction, and LLM invocation with @traceable.

LangSmith would then display every stage as a separate run.

By inspecting inputs and outputs of each run, I could determine
whether the issue originated from document retrieval, prompt
construction, business logic, or the LLM itself.

15. MOST IMPORTANT INTERVIEW QUESTION
============================================================

Question:

Explain @traceable with Thread, Trace, and Run.

Answer:

Thread represents an entire conversation.

Each user message creates a Trace.

Inside a Trace, multiple Runs are created.

Whenever a function is decorated with @traceable, LangSmith
automatically records that function as a Run.

Example:

Thread
│
├── User Question 1
│     └── Trace
│           ├── retrieve_documents()
│           ├── build_prompt()
│           └── generate_response()
│
├── User Question 2
│     └── Trace
│           ├── retrieve_documents()
│           ├── build_prompt()
│           └── generate_response()

Here:

Thread = Conversation

Trace = Request

Run = Function Execution

@traceable = Run Creator
